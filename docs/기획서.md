## 1. 한 줄 정의
**질문할 수 없는 상태의 유족을, 질문할 수 있는 상태로 만든다.**
가족을 잃은 사람이 손에 쥔 서류를 사진으로 올리면, AI가 읽고 → 내 가족의 상황을 파악해 → 언제까지 무엇을 어디서 해야 하는지를 알아봐준다.
### 문제
장례가 끝난 다음 날부터 행정이 몰려온다. 사망신고, 안심상속 신청, 보험 청구, 명의이전, 상속세. 유족은 슬퍼할 시간에 서류를 뒤진다.
더 깊은 문제는 따로 있다. **유족은 자기 상황을 모른다.** 아버지 서랍에서 나온 서류가 스무 장인데 그중 뭐가 중요한지 모른다. 통지서에 "○○캐피탈 4,200만 원"이 적혀 있어도 그게 위험 신호인지 판단할 수 없다. 애초에 **"내가 상속포기를 검토해야 하는 상황인가?"라는 질문 자체가 떠오르지 않는다.**
### 인간다움
AI가 위로를 흉내내지 않는다. AI는 서류를 읽고 절차를 알아본다. 사람은 애도할 시간을 되찾는다.

## 2. 왜 이 서비스여야 하는가 ★
발표와 Q&A에서 반드시 나올 두 질문이다. 답이 준비되지 않으면 이 프로젝트는 무너진다.
### Q. "그냥 ChatGPT에 물어보면 되지 않나요?"
판단 기준은 하나다.
> **사용자가 무엇을 물어야 할지 아는가?**
안다면 LLM 래퍼다. 만들 가치가 없다. **모른다면 서비스가 필요하다. 유족은 모른다.**
ChatGPT에 "아버지가 돌아가셨어요"라고 치면 일반 체크리스트가 나온다. 꽤 정확하다. 그런데 그건 인터넷에도 있다. 유족에게 없는 건 체크리스트가 아니라 **"내 경우에 해당하는 게 무엇인가"**이고, 그건 자기 서류를 읽을 수 있어야 나온다.
| | ChatGPT | 우리 |
|---|---|---|
| 입력 | 사용자가 자기 상황을 **이미 알아야** 질문 가능 | 서류 사진만 있으면 됨 |
| 결과 | 일반 체크리스트 | 내 자산·부채 기반 개인화된 할 일 |
| 지속성 | 세션 종료 시 소멸 | 6개월~1년 프로세스를 상태로 보유 |
| 기한 | 날짜 산술 오류 잦음 | 검증된 룰 엔진 + 근거 법령 표시 |
| 책임 | 틀려도 책임 없음 | 출처 명시, 판단은 사용자·전문가 |
**따라서 서류 파싱(F1)은 편의 기능이 아니라 이 서비스의 존재 이유 전부다.** 파싱을 빼면 ChatGPT로 대체된다. 파싱이 중심이면 대체 불가능하다.
### Q. "왜 에이전트여야 하나요? 룰 엔진이면 되지 않나요?"
기한 계산과 할 일 템플릿만 놓고 보면 맞는 지적이다. 에이전트가 **없으면 성립하지 않는** 지점은 아래 셋이다.
**① 롱테일 기관 절차 — 결정적 논거**
조회 결과에 "○○캐피탈 대출", "△△새마을금고 예금"이 나왔다. 그 기관의 상속 처리 절차는? 필요 서류는? 지점 방문이 필요한가, 비대면이 되나?
**한국의 금융기관·공공기관은 수천 개고, 절차가 전부 다르고, 계속 바뀐다.** 데이터로 미리 채우는 건 불가능하다. 에이전트가 검색해서 그 기관의 절차를 찾아오는 것 — 이건 룰 엔진으로 대체할 수 없다.
**② 할 일 조합의 폭발**
부동산 유무 × 사업자 유무 × 배우자 생존 × 미성년 자녀 × 채무 초과 × 형제 수 × 해외 자산. 경우의 수가 수백 개다. 하드코딩하면 대부분의 케이스에서 틀린 목록이 나온다. 에이전트가 서류를 읽고 **"이 가족의 경우"를 추론해** 목록을 구성해야 한다.
**③ 누락 감지**
"예금 거래내역에 자동이체가 4건 있는데 해지 대상 구독이 안 잡혔습니다." 규칙으로는 못 짜고, 유족이 가장 많이 놓치는 부분이다.
### 발표 한 줄
> **체크리스트는 이미 인터넷에 있다. 없는 건 "내 경우엔 어디로 가야 하는가"다.**
### 2-1. 적격성 심사 대응 — 왜 이게 제일 중요한가 ★★
심사기준 9페이지의 "적격성 심사"는 **배점이 아니라 Pass/Fail 게이트**다. 그중 첫 항목이 "주제 부합성 — AI를 통해 인간다움을 드러내는 서비스에 부합하는가"이고, 이 평가는 **에이전트가 1차 자동 판정**한다(11페이지). 여기서 탈락하면 채점 자체를 받지 못한다. 배점 항목보다 우선순위가 높다.
**주제 해석은 두 갈래다.**
| 해석 | 내용 | 평가 |
|---|---|---|
| A. AI가 사람인 척한다 | 챗봇이 위로하고, AI가 추도문을 쓰고, 감정적으로 곁에 있는 척 | 대회 취지("AI는 목적이 아닌 도구", 7페이지)와 충돌 위험 |
| **B. AI가 사람이 아닌 일을 대신해 사람이 사람다운 일을 할 시간을 되찾는다** | 행정·서류·기한 계산을 AI가 가져가고, 사람은 애도하고 가족과 함께 있는다 | **우리의 방향. 대회 주제를 정면으로 충족** |
실체는 이미 있다. 문제는 **표현 순서**다 — 발표에서 기능(F1~F5)을 먼저 보여주면 "행정 자동화 서비스"로만 읽힌다. 그래서 세 가지를 반드시 지킨다.
1. **발표를 장면으로 연다.** "장례식이 끝난 다음 날, 유족은 슬퍼할 새도 없이 서류를 붙듭니다" — 기능보다 사람이 먼저 나온다.
2. **F6(가족 공유)을 부가기능이 아니라 클로징으로 쓴다.** 서류 처리는 수단이고, 형제가 혼자 짊어지지 않고 함께 애도하게 되는 것이 목적이다. 데모의 마지막 장면은 F6이어야 한다.
3. **README·발표자료 첫 문장에 §2의 논지를 그대로 박는다.** 적격성 심사가 AI 자동 판정이므로, 그 AI가 문서 앞부분에서 "인간다움"과의 연결을 바로 읽을 수 있어야 한다.

## 3. 경쟁 서비스
| 서비스 | 하는 일 | 못 하는 일 |
|---|---|---|
| **정부24 안심상속 원스톱** | 재산·부채를 한 번에 조회 | 결과를 받아든 뒤 뭘 해야 하는지 안 알려줌 |
| **온여정** (베타) | 30일 체크리스트 카톡 발송, 전문가 매칭 | **대표가 수동으로 처리. AI 없음.** 확장 불가 |
| **고이** (누적 119억 투자) | 장례 3일 중심, 정찰제 상조 | 사후 행정은 부가 서비스 |
| **헬프미 등 법률 플랫폼** | 정보 콘텐츠, 상담 연결 | 개인화 없음 |
| **Empathy** (미국) | 아래 상세 | 한국 미진출, 제도 상이 |
### Empathy 상세 (가장 유사한 글로벌 사례)
**제품 5종** — Loss Support(사별 후 실무) / LifeVault(생전 유산 설계) / Caregiving Support(돌봄, 2026 신규) / Leave Support(사별·돌봄 휴직) / Connect(기관용)
**Loss Support 커버 범위 6개 영역** — 장례 준비, 수급권·보험금 청구, 계정·구독 해지 대행, 애도 지원, 주택 처리, 프로베이트(상속 검인) 안내
**성과** — NPS 75 · 만족도 4.8/5 · 92%가 "나아졌다" · 평균 **$3,007 절약** · 사용자당 **212시간 절약** · 5,000만 명 커버 · Prudential, MetLife, NYL, AT&T 등 제휴
**핵심 차이 3가지**
1. **중심이 사람이다.** 전담 Care Manager가 배정되어 플랜을 짜고 실행을 대행한다. AI는 2026년 7월에야 본격 도입됐고, 회사가 밝힌 AI의 역할은 *"Care Team의 인지 부하를 줄여 더 곁에 있게 하는 것"*이다. 첫 AI 기능인 LifeVault Conversations도 **어려운 대화를 연습하는 공간** — 서류를 읽는 쪽이 아니다.
2. **B2B2C다.** 보험사·고용주에 판매하고 유족은 무료로 쓴다. 개인 직접 판매가 아니다.
3. **제도가 다르다.** 미국은 프로베이트(법원 주도 검인) 체계, 한국은 상속포기 3개월·상속세 6개월 같은 **당사자 신고 기한** 체계다. Empathy가 한국에 진출해도 이 부분은 새로 만들어야 한다.
**발표에 쓸 것** — Empathy의 AI 철학("기술이 사람을 대체하는 게 아니라, 사람이 사람에게 쓸 여력을 만든다")은 우리와 같다. 5,000만 명을 커버하는 회사가 같은 결론에 도달했다는 건 강력한 뒷받침이다. 그리고 그 전환이 **3주 전(2026.07.07)** 발표됐다는 건 이 영역이 지금 움직이고 있다는 증거다.

## 4. 사용자와 시나리오
**주 사용자** 부모를 여읜 40~60대 자녀. 상속을 처음 겪는다. 법률·세무 용어를 모른다. 회사를 다니면서 처리해야 한다.
**핵심 시나리오 (데모 시나리오로 그대로 사용)**
1. 아버지가 3주 전 돌아가셨다. 장례는 끝났다.
2. 사망진단서를 사진으로 올린다 → 사망일이 자동 인식된다.
3. 남은 기한이 한 화면에. **상속포기·한정승인까지 68일 남음**이 맨 위에 붉게 뜬다.
4. 안심상속 조회 결과 통지서를 올린다 → 예금 1,200만 원 / 대출 8,400만 원이 구조화된다.
5. **"부채가 자산보다 많습니다. 한정승인·상속포기 검토 기한이 68일 남았습니다."**
6. 목록에 낯선 기관이 있다. **에이전트가 해당 기관의 상속 처리 절차를 찾아온다** — 필요 서류, 접수 방법, 비대면 가능 여부.
7. 할 일을 형에게 공유한다. 형이 링크로 들어와 두 건을 맡는다.

## 6. 데모 범위 — 판단 결과
**파싱은 좁게, 커버리지는 넓게.**
- **서류 종류는 3종에서 절대 늘리지 않는다.** 여기가 깨지면 데모가 무너진다.
- **할 일 템플릿은 30개까지 넣는다.** 코드가 아니라 데이터 입력이라 하루면 되고, 체감 범위가 3배가 된다. 심사위원은 타임라인 화면에서 항목 수를 본다.
- **에이전트 탐색 대상 기관은 5~10개로 한정**하고 폴백을 확실히 둔다.
### 지원 서류 3종
| 서류 | 뽑아낼 것 | 왜 이것인가 |
|---|---|---|
| 사망진단서 / 사망신고서 | 사망일, 고인 성명 | **모든 기한의 기준점**. 이거 하나로 타임라인 전체 생성 |
| 안심상속 조회 결과 통지서 | 금융자산·채무 목록, 기관명, 금액 | 상속 판단의 유일한 근거. 에이전트 탐색의 입력 |
| 보험증권 / 각종 고지서 | 보험사, 증권번호, 계약자 | 청구·해지 액션의 소스 |

## 7. 핵심 기능
### F1. 서류 업로드 → 구조화 ★ 서비스의 존재 이유
**입력** 사진 또는 PDF (여러 장 동시)
**처리** Upstage Document Parse → Solar로 서류 종류 분류 → Information Extract로 스키마 추출
**출력** 추출된 필드 + **원문 위치 하이라이트** + 신뢰도
수용 기준
- 샘플 3종 각 5장, 총 15장에서 핵심 필드 추출 성공률 90% 이상
- 추출 실패 시 **수동 입력 폴백 UI 필수**
- 추출값 옆 **"원문에서 확인"** → 원본 이미지의 해당 영역 표시 (AI를 믿게 만드는 장치)
### F2. 기한 역산 타임라인
**입력** 사망일 → **출력** D-day 순 정렬된 할 일 30개
```
{ id, 제목, 기준일_계산식, 마감일, 남은일수,
  담당기관, 필요서류[], 근거법령, 온라인신청링크,
  담당자, 상태: 미시작|진행중|완료|해당없음 }
```
수용 기준
- 모든 항목에 **근거 법령 표시**
- 지난 기한은 회색 처리하되 숨기지 않음
- 기한 없는 항목(통신·구독 해지, 명의이전 등)은 "권장 시점" 섹션으로 분리
### F3. 상속 판단 신호등 ★ 킬러 기능
| 신호 | 조건 | 메시지 |
|---|---|---|
| 🔴 위험 | 부채 > 자산 | "부채가 자산보다 {금액} 많습니다. 한정승인 또는 상속포기 검토가 필요할 수 있습니다. 기한 D-{n}" |
| 🟡 주의 | 부채가 자산의 50% 이상 | "채무 비중이 높습니다. 전문가 상담을 권합니다" |
| 🟢 안정 | 부채 < 자산의 50% | "단순승인으로 진행 가능해 보입니다" |
3개월을 놓치면 유족이 빚을 그대로 떠안는다. **발표의 클라이맥스.**
반드시 병기: **"본 서비스는 정보 제공이며 법률 자문이 아닙니다. 최종 판단은 변호사·법무사와 상의하세요."**
### F4. 할 일 상세 — "무엇을 들고 어디로"
- 내 상황에 맞게 개인화된 준비물 체크리스트 (부동산 없으면 등기 서류 제외)
- 접수처 + 온라인 신청 가능 여부 + 링크
- 근거 법령 원문 링크
- Solar가 생성한 3~4문장 안내문. 초등학생도 이해할 언어로, 전문 용어는 괄호로 풀어씀
### F5. 기관별 절차 탐색 에이전트 ★ 신규 · 에이전트의 존재 이유
**입력** F1에서 추출된 기관명 (예: "○○캐피탈")
**처리** 에이전트 루프
```
기관명 → 사전 구축 DB 조회
   ↓ (없으면)
웹 검색 도구 호출 → 결과에서 상속 처리 절차 추출
   ↓
스키마로 정리 { 필요서류[], 접수방법, 비대면가능, 문의처, 출처URL, 신뢰도등급 }
   ↓
캐시 저장 (다음 사용자를 위해)
   ↓ (실패 시)
폴백: 기관 대표번호 + "직접 문의 필요" 안내
```
**출력** 해당 기관의 상속 처리 절차 카드 + **출처 링크**
**기관 신뢰도 3단계 — 실제 검색으로 검증한 결과**
착수 전 국민은행·새마을금고·롯데캐피탈로 실검색을 해봤다. 기관 등급에 따라 결과 품질이 확연히 다르다.
| 등급 | 예시 | 검색 결과 품질 | 화면 동작 |
|---|---|---|---|
| 1등급 · 대형 은행 | 국민은행, 하나은행 등 | 금액별 절차·필요서류·비대면 가능 여부까지 구조화된 안내 페이지 존재 | 절차 카드 전체 표시 |
| 2등급 · 상호금융 | 새마을금고, 신협 등 | 개념(대표상속인 지정 등)은 나오나 서류 목록은 "지점 문의"로 귀결 | 부분 정보 + 지점 문의 안내 |
| 3등급 · 비은행·캐피탈 | 캐피탈사, 저축은행 등 | 기관 고유 절차 정보 거의 없음. 일반 상속법 설명만 검색됨 | **대표번호 폴백만 표시** |
**중요**: F3 킬러 시나리오(부채 > 자산)에 가장 자주 등장하는 기관이 3등급(캐피탈·저축은행)이다. 즉 데모의 핵심 순간에 오히려 폴백이 뜰 확률이 높다.
**그래서 폴백을 실패가 아니라 설계 원칙으로 재정의한다.** "AI가 모든 걸 아는 척하지 않고, 모르면 대표번호를 준다"는 F3의 "판단은 사람에게" 원칙과 같은 톤이다. 발표에서 1등급·3등급 기관을 **의도적으로 둘 다** 시연해 이 설계가 정직하다는 걸 보여준다.
수용 기준
- 주요 기관 5~10개를 **1·2·3등급 섞어서** 사전 캐시 (데모 안정성 확보)
- 캐시 미스 시에도 30초 안에 결과 또는 폴백 반환
- 출처 URL 없는 결과는 **표시하지 않는다** (환각 방지)
- 폴백 응답도 "확인되지 않음"과 "확인함" 둘 다 UI상 명확히 구분
> ⚠️ 데모에서는 검증된 기관만 시연한다. 라이브 검색은 리스크가 크다.
### F6. 가족 공유 ★ 데모 클로징
할 일별 담당자 지정 + 링크 공유. 형제가 나눠 맡는다.
구현은 담당자 필드 + 공유 링크 정도로 가볍지만, **유족 행정의 진짜 고통은 혼자 떠안는 것**이라는 서사를 만든다. §2-1에서 정한 대로, **데모의 마지막 장면은 이 화면이어야 한다** — 서류 처리는 수단이고, 형제가 함께 애도하게 되는 게 목적이라는 걸 보여주는 장면.
### F7. 정적 콘텐츠 — 팁 카드 (스트레치, 커뮤니티 아님) ★ 신규
"커뮤니티를 만들자"는 논의에서 출발했지만, 실시간 커뮤니티는 짓지 않는다 (§8 참고). 대신 **팀이 실제로 조사한 내용을 정적으로 심는다.**
**포함하는 것**
- **팁 카드 10~20개**: "유족이 자주 놓치는 것" 같은 짧은 카드. 팀이 검색·조사해서 직접 작성. 가능하면 출처 링크 병기
- 배치: 대시보드 하단 또는 할 일 상세 사이드
**포함하지 않는 것**
- 사용자 계정, 글쓰기, 댓글 — 이건 §8에서 제외한 실시간 커뮤니티의 영역
- **지어낸 "유가족 후기"** — 애도를 다루는 서비스에서 없는 사람의 슬픔을 지어내 진짜처럼 보여주는 건 하지 않는다. 넣고 싶다면 "예시 상황입니다"라고 명확히 라벨링하거나, 아예 뺀다
**왜 이게 "더미 데이터 대충 채우기"와 다른가**
화면과 개발 비용은 거의 같다. 다른 건 **정직성**이다. "커뮤니티"라고 부르면 다른 사용자의 존재를 암시하게 되고, 심사위원이 "이거 실제 사용자인가요?"라고 물으면 신뢰가 깎인다. "저희가 조사한 팁"이라고 부르면 같은 화면이 오히려 실용성 심사에서 리서치 근거로 읽힌다.
수용 기준
- 콘텐츠는 실제 검색·조사 결과로 작성 (무작위 생성 금지)
- 사용자 후기 형태를 쓸 경우 반드시 "예시" 라벨 표시
- 개발 비용 반나절 이내. **8/2에 시간이 남으면 넣는 최하위 우선순위 스트레치**

## 9. AI 파이프라인 설계
```
서류 이미지
   ↓
[Upstage Document Parse]        표·레이아웃 보존 텍스트 추출
   ↓
[Solar] 서류 종류 분류          3종 중 하나로 라우팅
   ↓
[Upstage Information Extract]   종류별 스키마 필드 추출
   ↓
[검증 레이어 · 코드]            날짜 형식, 금액 합계, 필수 필드 체크
   ↓
   ├─→ [룰 엔진 · 코드]         기한 계산 ※ LLM에 절대 맡기지 말 것
   ├─→ [에이전트 · F5]          기관 절차 탐색 (검색 도구 + 캐시)
   └─→ [에이전트 · 상황 추론]   할 일 집합 구성 + 누락 감지
   ↓
[Solar] 안내문 생성 · 용어 변환
   ↓
화면
```
### 설계 원칙 — 발표에서 반드시 말할 것
> **판단과 계산은 코드가, 읽기와 탐색과 설명은 AI가 한다.**
기한 계산을 LLM에 맡기면 환각이 난다. 법정 기한은 룰 엔진에 상수로 박고, LLM은 문서를 읽고 절차를 찾아오고 사람 말로 옮기는 역할만 한다. 이 분리 자체가 **AI 활용도 "결과물 품질 기여도" 5점**의 근거다.
### 법령 원문 확보 — RAG 대신 정적 주입
법정 기한(§12, 8개 조문)에 RAG(임베딩·벡터 검색)는 쓰지 않는다. 문서가 8~30개뿐인데 벡터 검색을 붙이면 정확도만 떨어지고, 심사 기준 "AI는 목적이 아닌 도구"와도 어긋난다. 대신 아래 중 하나로 **한 번 수집해 정적 파일로 굳힌다.**
| 방법 | 방식 | 시간 | 권장도 |
|---|---|---|---|
| **방법 1 · 수동 복사** | 국가법령정보센터(law.go.kr)에서 조문 8개를 검색해 JSON에 직접 붙여넣기 | 1시간 | **기본. 조문이 안정적이라 이걸로 충분** |
| 방법 2 · 법제처 오픈API | data.go.kr에서 개발계정(트래픽 1만 건) 신청 → 법령 본문 조회 API로 조문 자동 수집 | 승인 대기 포함 반나절~1일 | 시간 남으면. "자동 갱신 구조"라고 발표에서 언급 가능 |
```json
{
  "민법_1019": {
    "법령명": "민법", "조문번호": "제1019조", "조문제목": "승인, 포기의 기간",
    "조문내용": "① 상속인은 상속개시있음을 안 날로부터 3월내에...",
    "출처": "https://www.law.go.kr/법령/민법/제1019조"
  }
}
```
Solar는 이 원문을 **검색하지 않고 받아서 쉬운 말로 바꾸는 역할만** 한다. 법령 내용 자체가 환각일 가능성이 없고, 원문을 화면에 병기해 검증도 가능하다.
**기관 절차(F5)는 반대로 간다.** 대상이 수천 개고 계속 바뀌어서 정적 파일로 못 굳힌다 — 그래서 거긴 캐시 우선 + 라이브 검색 에이전트 구조를 쓴다. **작고 고정된 데이터는 정적 주입, 크고 변하는 데이터는 검색 에이전트**라는 구분이 두 기능 설계의 핵심 원칙이다.
### Upstage API 3종 전부 사용 → 가점 +5
| API | 사용 위치 |
|---|---|
| Document Parse | 서류 이미지 → 구조화 텍스트 |
| Information Extract | 텍스트 → 스키마 필드 |
| Solar LLM | 서류 분류, 에이전트 추론, 안내문 생성 |

## 10. 개발 프로세스의 AI 통합 (배점 15점 — 놓치기 쉬움)
"개발 프로세스 전반의 AI 통합" 10점 + "에이전트 설정·지침 체계성" 5점은 **제품이 아니라 개발 방식**을 본다.
- **`CLAUDE.md` / `AGENTS.md`** — 프로젝트 규칙, 코딩 컨벤션, 상속 도메인 용어집, 금지사항(법률 자문 표현 금지 등)
- **`prompts/`** — 프롬프트를 코드처럼 파일로 버전 관리. 변경 이력이 커밋에 남게
- **`agents/`** — F5 에이전트의 시스템 프롬프트, 도구 정의, 종료 조건, 실패 처리 정책을 문서화. **여기가 "에이전트 지침 체계성" 5점의 직접 근거**
- **`evals/`** — 샘플 15장의 정답 JSON + 추출 정확도 측정 스크립트. 프롬프트 변경 시마다 실행
- **커밋 메시지에 AI 사용 흔적**
- **`docs/AI_활용_기술서.md`** — 제출물 4번. 모델·API 사용 위치·프롬프트·검증 결과를 표로
> ⚠️ README·주석에 심사 지시를 넣는 프롬프트 인젝션은 **적발 시 실격**. 절대 금지.

## 11. 데이터 — 샘플 서류 확보
실제 유족 서류는 구할 수 없다. 다음으로 만든다.
1. 정부24·법원·국세청에서 **공개 서식 PDF** 내려받기 (빈 양식)
2. 가상 인물 3명의 시나리오
   - A: 자산 > 부채 (정상 상속)
   - B: 부채 > 자산 (상속포기 케이스) ← **데모 주인공**
   - C: 부동산 포함 복합 케이스
3. 양식에 가상 데이터를 채워 인쇄 → **실제로 휴대폰으로 촬영**. 기울기·그림자·구김 있는 상태로. 이게 진짜 입력 조건이다
4. 각 이미지에 대응하는 정답 JSON 작성 → `evals/` 기준 데이터
**이 과정 자체를 발표에 넣는다.** 실제 사용 조건을 고민했다는 증거다.

## 14. 기술 스택
**권장: Next.js 단일 레포 + Vercel 배포**

> ⚠️ 실제 구현(`agent_and_ui` 브랜치)은 Next.js가 아니라 **Vite + React + TS**로
> 갔고, DB(Supabase)도 아직 안 붙었음 — 클라이언트 상태(`caseState`)를 매 요청마다
> 서버로 통째로 보내는 방식. 아래 표는 기획 당시 계획이며 실제와 다를 수 있음.

| 레이어 | 선택 | 이유 |
|---|---|---|
| 프레임워크 | Next.js (App Router) + TypeScript | 프론트·API 한 곳. 배포 링크 확보 5분 |
| 스타일 | Tailwind CSS | 속도 |
| API | Route Handler에서 Upstage REST 직접 호출 | 배포 대상 1개 유지 |
| 에이전트 | 함수 호출 루프 + 웹 검색 도구 + 결과 캐시 테이블 | 프레임워크 없이 직접 구현이 더 빠름 |
| DB | Supabase (Postgres) | 무료, 파일 스토리지 포함 |
| 배포 | Vercel | 커밋 시 자동 배포 |
### 데이터 모델
```
Case           id, 사망일, 고인명, 생성일, 공유토큰
Document       id, case_id, 종류, 원본URL, 추출JSON, 신뢰도
Asset          id, case_id, 구분(자산|부채), 기관명, 종류, 금액
Task           id, case_id, 템플릿id, 마감일, 상태, 담당자, 개인화_안내문
TaskTemplate   id, 제목, 기한_규칙, 기관, 필요서류[], 근거법령, 링크
Institution    id, 기관명, 절차JSON, 출처URL, 갱신일   ← F5 캐시
```

## 17. 예상 질문과 답변 ★
발표 마지막에 **선제적으로 슬라이드 1장**을 넣는다. 질문받기 전에 먼저 답하면 오히려 점수가 된다.
| 질문 | 답 |
|---|---|
| **"ChatGPT로 되지 않나요?"** | 왼쪽에 ChatGPT 일반 체크리스트 스크린샷, 오른쪽에 우리 화면(내 서류 기반 신호등 + D-68). "유족은 무엇을 물어야 할지 모른다"가 핵심 |
| **"에이전트가 왜 필요한가요?"** | 한국 금융기관은 수천 개, 절차가 전부 다르고 계속 바뀐다. 데이터로 못 채운다 |
| **"이미 있는 서비스 아닌가요?"** | 온여정=수동 컨시어지, Empathy=미국·B2B2C·제도 상이, 안심상속=조회만. **먼저 언급하고 차별점을 대라** |
| **"법률 자문 아닌가요?"** | 판단하지 않는다. 기한과 선택지, 근거 법령만 제시. 전 화면에 고지 |
| **"정확도는요?"** | `evals/` 측정 리포트 제시. 실패 시 수동 입력 폴백 |
| **"이거 그냥 법률·행정 서비스 아닌가요? 인간다움과 무슨 상관이죠?"** | §2-1 참조. AI가 행정을 가져가서 사람이 애도할 시간을 되찾는 것 자체가 주제 부합. 클로징 화면(F6)으로 답을 보여준다 |
| **"이 팁, 실제 사용자 데이터인가요?"** | 아니다. 팀이 조사·작성한 정적 콘텐츠라고 정직하게 답한다. 계정도, 게시판도 없다 |
| **"캐피탈사 같은 곳은 절차를 못 찾을 것 같은데요?"** | 맞다. 3등급 기관은 대표번호 폴백을 보여준다. 모르면 모른다고 말하는 게 설계 원칙이라고 답한다 (F5 신뢰도 등급표 제시) |
